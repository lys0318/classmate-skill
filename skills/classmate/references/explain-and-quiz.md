# 기능 완성 시 설명과 퀴즈

SKILL.md의 공통 규칙과 난이도 표를 함께 따른다. 이 흐름 동안 프로젝트 코드는 고치지 않는다.

자동 실행(SKILL.md의 "자동 실행 판단"을 통과한 경우)은 모드가 `가볍게`면 0절, `꼼꼼하게`면 1절부터 시작한다. 사용자가 직접 부른 경우는 모드와 상관없이 맨 아래 "직접 불렀을 때"부터 시작한다.

## 0. 가볍게 기록

퀴즈 없이 짧은 노트만 남긴다. 토큰을 적게 쓰면서, 나중에는 알 수 없는 "왜 이렇게 만들었는지"와 "막혔던 것"을 지금 기록해 두는 것이 목적이다.

1. 다룰 기능은 1절과 같다. 여러 개면 기능마다 노트를 하나씩 쓴다.
2. 기능마다 5절 형식의 노트를 `status: noted`로 쓴다. `## 설명`의 네 줄은 2절 기준과 같다. `## 퀴즈` 절은 쓰지 않는다. 대화창에는 설명을 보여주지 않는다.
3. 평소 작업 보고 끝에 한 줄만 알리고, 질문하지 않는다.
   - 기능 하나: `📝 classmate: '할 일 추가' 기록함 (퀴즈는 review 때)`
   - 여러 개: `📝 classmate: '할 일 추가', '할 일 삭제' 기록함 (퀴즈는 review 때)`
4. **중간 점검 제안:** 노트를 쓴 뒤 `features/`에서 `status: noted`인 노트 수를 센다. 그 수가 5의 배수(5, 10, 15…)일 때만 알림 바로 다음 줄에 이렇게 붙인다. 5의 배수가 아니면 아무것도 붙이지 않는다.
   `기록이 <N>개 쌓였어요. /classmate review로 중간 점검해 볼까요?`

## 1. 다룰 기능

- 마지막 학습 노트 이후 이번 대화에서 완성한 기능들을 다룬다.
- 여러 개면 묶어서 한 번에 다룬다. 학습 노트는 기능마다 따로 쓴다(5절).
- 평소 작업 보고를 먼저 마치고, 같은 응답 끝에 이어서 진행한다.

## 2. 설명

기능마다 10줄 안팎으로 쓴다. 깊이는 config의 난이도를 따른다.

- **바뀐 파일**
- **흐름:** 데이터가 지나가는 길을 화살표 한 줄로. 예: `입력창 → addTodo() → todos 배열 → render()`
- **이유:** 이 방식을 고른 이유와 고려한 대안
- **막혔던 것:** 중간에 생긴 문제와 해결 과정

이유나 막혔던 것이 이번 대화에 없으면 지어내지 않는다. 이유는 `기록 없음`, 막혔던 것은 `없음`으로 쓴다.

## 3. 노트 먼저 저장, 그다음 지금 / 나중에

1. **묻기 전에 저장한다.** 4절 규칙대로 문제를 만들고(정답·해설 포함), 5절 형식의 학습 노트를 `status: deferred`, 모든 문제 `결과: 미응답`으로 먼저 쓴다. 사용자가 답하지 않거나 세션이 끊겨도 기록이 남게 하기 위해서다.
2. 설명 바로 뒤에 퀴즈를 지금 풀지 나중에 풀지 묻는다. 기능이 여러 개여도 한 번만 묻는다.
   - 선택지 UI 도구(Claude Code의 AskUserQuestion 등)가 있으면 쓰고, 없으면 `1. 지금  2. 나중에`처럼 번호로 받는다.
   - **지금:** 4절로 간다.
   - **나중에:** 노트는 이미 저장돼 있다. 다음에 classmate를 부르거나 review를 할 때 다시 나온다고 알리고 끝낸다.
   - **답 대신 다른 요청을 하거나 질문을 취소하면:** '나중에'와 같다. 퀴즈를 미뤄 뒀다고 한 줄로 알리고 그 요청을 진행한다.

## 4. 퀴즈

### 구성

- 기능 하나: 3문제(객관식 2 + 서술형 1).
- 기능 여러 개: 모두 합쳐 3~5문제. 기능마다 최소 1문제.
- 문제마다 영역 하나를 붙인다: `구조`, `코드`, `데이터 흐름`, `설계 이유`, `문제 해결`. 한 번에 내는 문제들은 가능하면 서로 다른 영역으로 한다.
- 객관식은 보기 4개에 정답 1개.

### 출제 원칙

- 이 프로젝트의 실제 코드와 이번 작업에 근거한다. 일반 상식 문제는 내지 않는다.
- 변수 이름이나 파일 이름을 외우게 하는 문제는 내지 않는다.
- "왜", "어디로", "만약 ~라면" 형태를 중심으로 낸다.
- 난이도 표에 맞춘다.
- `설계 이유`, `문제 해결` 문제는 이번 대화나 노트에 근거가 있을 때만 낸다.

### 묻는 방법

- 객관식: 선택지 UI 도구가 있으면 한 번에 묻는다. 없으면 문제와 보기를 번호와 함께 보여주고 번호로 받는다.
- 서술형: 대화로 답을 받는다.
- "모르겠다"는 틀림으로 처리한다.
- 도중에 그만두거나 다른 요청으로 넘어가면 남은 문제는 `미응답`으로 둔 채 그 요청을 진행한다.

### 채점과 해설

- 객관식은 `맞음` 또는 `틀림`.
- 서술형은 핵심을 다 담으면 `맞음`, 일부만 담으면 `부분`, 아니면 `틀림`.
- 문제마다 결과를 보여준다. `틀림`·`부분`이면 정답, 이유, 관련 코드 위치(`파일:줄`)를 알려준다.
- 마지막에 맞힌 개수를 한 줄로 알린다.
- 채점할 때마다 노트의 `내 답:`·`결과:`를 채운다. 모든 문제에 답하면 `status: done`으로 바꾼다.

## 5. 학습 노트

`.classmate/features/NNN-<slug>.md`에 기능마다 하나씩 쓴다. 3절에서 묻기 전에 먼저 쓰고, 답을 받으면 고친다. `features/` 폴더가 없으면 만든다.

- **NNN:** `features/`에 있는 파일 번호 중 가장 큰 값 + 1을 3자리로 쓴다. 처음이면 `001`.
- **slug:** 기능 이름에서 공백을 `-`로 바꾸고 `/ \ : * ? " < > |`를 지운다. 한글은 그대로 둔다. 예: `할 일 추가` → `001-할-일-추가.md`

형식(이 형식을 그대로 지킨다. review와 리포트가 이 형식을 읽는다):

```markdown
---
id: 001
feature: 할 일 추가
date: 2026-11-24
status: done
level: 중급
---
## 설명
- 바뀐 파일: src/todo.js, src/app.js
- 흐름: 입력창 → addTodo() → todos 배열 → render()
- 이유: Map도 고려했지만 순서 유지가 쉬운 배열을 택했다
- 막혔던 것: 빈 입력이 추가되는 버그 → trim 검사로 해결

## 퀴즈
### Q1 [데이터 흐름] 객관식
문제: 사용자가 '추가' 버튼을 누르면 입력한 글자는 어디에 저장되나요?
보기: ① localStorage ② todos 배열 ③ 서버 ④ input 요소
정답: ②
내 답: ③
결과: 틀림
해설: addTodo()가 todos 배열에 push한다 (src/todo.js:7)

### Q2 [설계 이유] 서술형
문제: 할 일을 Map이 아니라 배열에 담은 이유는 무엇인가요?
정답: 추가한 순서를 그대로 유지하며 화면에 그리기 쉬워서
내 답: 순서대로 보여주려고
결과: 맞음
해설: render()가 todos.map으로 순서대로 그린다 (src/app.js:8)
```

- `id`는 파일 이름의 NNN과 같다. `date`는 오늘 날짜(YYYY-MM-DD). `level`은 지금 난이도.
- `status`는 모든 문제에 답했으면 `done`, 답하지 않은 문제가 하나라도 있으면 `deferred`. 가볍게 모드로 기록만 했으면 `noted`이고, 이때는 `## 퀴즈` 절이 없다.
- 문제 헤더는 `### Q<번호> [<영역>] <객관식|서술형>` 형식이다.
- 서술형에는 `보기:` 줄을 쓰지 않는다.
- `결과:`는 `맞음`, `부분`, `틀림`, `미응답` 중 하나다.
- 답하지 않은 문제는 `내 답:`을 비우고 `결과: 미응답`으로 둔다. 정답과 해설은 미리 써 둔다.

## 직접 불렀을 때

사용자가 인자 없이 classmate를 부르면 자동 실행 판단 없이 진행한다.

1. `.classmate/config.json`이 없으면 먼저 `on`으로 켜라고 알리고 끝낸다. `enabled`가 `false`여도 직접 불렀으므로 진행한다.
2. **밀린 퀴즈 먼저.** `status: deferred`(미룬 퀴즈)나 `status: noted`(기록만 된 기능)인 노트가 있으면, 첫 메시지에서 그 기능 이름들을 구분해 알려주고 지금 풀지 묻는다. 모드와 상관없이 그렇게 한다.
   - 풀면, `noted` 노트는 먼저 기능마다 4절 규칙으로 3문제(객관식 2 + 서술형 1)를 만들어 그 노트에 `## 퀴즈` 절로 쓰고 `status: deferred`(모두 `미응답`)로 바꾼다. 노트의 이유가 `기록 없음`이면 `설계 이유` 문제는 내지 않는다.
   - 그다음 `결과: 미응답`인 문제를 4절 방식으로 묻고 채점한 뒤, 그 노트의 `내 답:`·`결과:`를 채운다. 모두 답했으면 `status: done`으로 바꾼다.
   - 한 번에 최대 10문제. 넘치면 오래된 노트부터 하고, 남은 기능 수를 알린다.
   - **밀린 퀴즈를 풀었으면** 맞힌 개수(와 남은 밀린 퀴즈 수)를 알리고 끝낸다. 3단계는 이번 대화에 아직 노트가 없는 작업이 있을 때만 이어서 한다. 다룰 것을 찾으려고 추가로 묻지 않는다.
   - 사용자가 미루면 `noted` 노트는 그대로 두고 3단계로 간다. 사용자가 그만하자고 하면 끝낸다.
3. **다룰 작업 정하기.**
   - 마지막 학습 노트 이후 이번 대화에서 한 작업이 있으면 그것을 다룬다.
   - 없으면 git 기록을 본다: 마지막 노트 날짜 이후의 커밋과 아직 커밋하지 않은 변경. 노트가 없으면 최근 커밋 몇 개. 이미 노트가 있는 기능(노트의 기능 이름·바뀐 파일과 겹치는 변경)은 다시 다루지 않는다.
   - 대화도 git 기록도 없거나 무엇을 다룰지 분명하지 않으면, 지어내지 말고 어떤 기능을 다루고 싶은지 사용자에게 묻는다.
   - 대화 없이 git 기록만으로 다루는 경우 이유와 막혔던 것은 알 수 없다. 설명에는 `기록 없음`·`없음`으로 쓰고, 문제는 `구조`, `코드`, `데이터 흐름` 영역에서만 낸다.
4. 이후는 2~5절과 같다.
