# classmate 빈도 모드와 '처음 배우기' 설계

- 작성일: 2026-11-26
- 상태: 승인됨 (2026-11-26)
- 앞선 설계: `docs/superpowers/specs/2026-11-24-classmate-skill-design.md` (이 문서는 그 위에 더한다)
- 표시: *(제안)* = 대화에서 사용자가 직접 정하지 않고 설계자가 정한 것

## 1. 왜

1. **토큰 부담.** 지금은 기능을 완성할 때마다 설명과 퀴즈를 낸다. 추정 비용은 기능 하나당 약 1만 토큰, review 한 번에 약 2~3만 토큰(작은 프로젝트)이다. 기능 하나를 바이브코딩으로 만드는 데 드는 5만~20만 토큰의 5~15% 정도다. 사용자는 이 부담을 줄이고 싶어 한다.
   - 다만 "왜 이렇게 만들었는지"와 "문제를 어떻게 풀었는지"는 그 순간의 대화에만 남는다. 모든 것을 마지막으로 미루면 이 두 가지가 사라진다.
   - 그래서 기본값은 **기능마다 짧게 기록만 하고, 퀴즈는 review에서 몰아서** 낸다.
2. **완성된 프로젝트로 공부하기.** 스킬을 나중에 설치한 사람도 쓸 수 있어야 한다. 대상은 두 가지다.
   - 이미 다 만든 **내 프로젝트**
   - 공부하려고 받은 **남의 프로젝트**(오픈소스 등)
   - 두 경우 모두 쉬운 설명과 이해도 퀴즈를 받는다.

## 2. 목표 / 비목표 / 안티목표

**목표**
- 기능 완성 시의 동작을 세 가지 모드로 고를 수 있다: `가볍게`(기본), `꼼꼼하게`(지금 방식), `직접만`.
- `/classmate learn`으로 완성된 프로젝트를 장(chapter)으로 나눠 공부한다. 장마다 쉬운 설명과 퀴즈가 나오고, 진행 상황은 세션이 바뀌어도 이어진다.
- 두 기능 모두 기존 학습 노트, review, 리포트와 이어진다.

**비목표 (이번에 하지 않음)**
- GitHub 주소를 받아 대신 내려받기. 사용자가 직접 clone한 뒤 그 폴더에서 실행한다.
- 프로젝트를 실행하거나 테스트를 돌려 동작을 보여주기
- 장 단위가 아닌, 프로젝트 전체를 한 번에 설명하기

**안티목표 (이렇게 되면 실패)**
- learn이 큰 프로젝트를 한 번에 다 읽어 토큰을 크게 쓴다.
- 남의 프로젝트의 설계 이유를 근거 없이 지어내거나, 추정을 사실처럼 쓴다.
- `가볍게` 모드인데 대화창에 한 줄보다 많이 끼어든다.
- 중간 점검 제안이 기능마다 반복돼 귀찮아진다.
- learn 때문에 남의 저장소에 커밋될 흔적이 생긴다.

## 3. 제약 (기존 설계에서 이어짐)

- 런타임 의존성 없음. 지시문 + 리포트 틀(인라인 JS)뿐이다.
- `.classmate/`는 스스로 커밋에서 빠진다(`.gitignore`에 `*`).
- 학습 노트 형식, `reviews/` 형식, `report-data.js` 형식은 기존 것을 유지하고 필요한 만큼만 넓힌다.
- Claude Code와 Codex 모두에서 동작한다.

## 4. 방식 (검토한 것과 선택)

| 결정 | 고른 것 | 뺀 것과 이유 |
|---|---|---|
| 토큰 줄이기 | 모드 설정(가볍게 기본) | "마지막에 한 번만": 이유와 문제 해결 기록이 사라져 스킬의 핵심 목적과 어긋난다 |
| 가볍게 모드의 퀴즈 | review에서 몰아서 | 기록 시점에 문제도 미리 만들어 두기: 문제 생성 비용이 다시 붙는다 |
| learn 단위 | 프로젝트 지도 → 장 단위 | 한 번에 전체 설명: 큰 프로젝트에서 토큰이 과하다 |
| 장 노트 저장 | 기존 `features/` 노트 형식 재사용 | 별도 폴더와 리포트 섹션: 리포트·검사기를 새로 만들어야 하고 얻는 게 없다 |
| learn과 `on`의 관계 | learn은 `on` 없이 동작하고 전역 지침 파일을 건드리지 않음 | learn 전에 `on` 요구: 남의 프로젝트에서는 기능을 만들 일이 없다 |

## 5. 빈도 모드

### 5.1 설정과 명령

- `config.json`에 `mode` 필드를 더한다: `"가볍게"` | `"꼼꼼하게"` | `"직접만"`.
- `mode`가 없는 기존 config는 `가볍게`로 본다. *(제안: 아직 실제 사용자가 없고, 새 기본값과 맞추는 쪽이 단순하다)*
- `on`: 난이도 다음에 모드를 묻는다. 기본값은 `가볍게`이고, 세 모드를 한 줄씩 설명한다.
- 새 명령: `/classmate mode 가볍게|꼼꼼하게|직접만` (Codex는 `$classmate mode …`). config가 없으면 먼저 `on`을 하라고 안내한다.

### 5.2 기능을 완성했을 때 (자동 실행 판단 이후)

| 모드 | 하는 일 |
|---|---|
| `가볍게` | 학습 노트를 `status: noted`로 저장한다. 설명 4줄만 쓰고 퀴즈는 없다. 대화창에는 한 줄만 알린다. 예: `📝 classmate: '할 일 추가' 기록함 (퀴즈는 review 때)` |
| `꼼꼼하게` | 지금 흐름 그대로다(설명 → 노트 미룸으로 먼저 저장 → 지금/나중에 → 퀴즈). |
| `직접만` | 아무것도 하지 않는다. |

- 자동 실행 판단 기준(기능 완성, 차례를 넘길 때, 작은 수정 제외 등)은 그대로다. `직접만`은 판단 단계에서 바로 빠진다.
- 기능 여러 개를 한 번에 완성했다면 `가볍게`에서도 노트는 기능마다 쓰고, 알림은 한 줄로 묶는다.

### 5.3 `noted` 노트 형식

기존 노트와 같고, 차이는 두 가지다.
- `status: noted`
- `## 퀴즈` 절이 없다

`## 설명`의 네 줄(바뀐 파일, 흐름, 이유, 막혔던 것)은 꼼꼼하게 모드와 같은 기준으로 쓴다. 이유와 막혔던 것이 대화에 없으면 `기록 없음`, `없음`으로 쓴다.

### 5.4 중간 점검 제안 *(제안)*

- `가볍게` 모드에서 기록 알림을 할 때, 지금 `status: noted`인 노트 수가 5, 10, 15…이면 알림 뒤에 한 줄을 붙인다.
  - 예: `기록이 5개 쌓였어요. /classmate review로 중간 점검해 볼까요?`
- 퀴즈를 내면 `noted`가 다른 상태로 바뀌므로(5.5) 수는 자연스럽게 줄어든다. 날짜로 세지 않는다.
- 5의 배수가 아닐 때는 제안하지 않는다(매번 반복하지 않기 위해).

### 5.5 `noted` 기능에 퀴즈를 낼 때 (review와 직접 부르기 공통) *(제안)*

- 문제는 **그 노트에 직접 쓴다.** 노트에 `## 퀴즈` 절을 더하고, 상태는 다음처럼 바뀐다.
  - 문제를 노트에 먼저 쓰면 `deferred`(모두 `미응답`)
  - 모두 답하면 `done`
  - 이후는 기존 노트와 똑같이 다룬다.
- 그래서 "아직 퀴즈를 안 낸 기능"은 `status: noted`인 노트다. 따로 표시하거나 review 파일을 뒤질 필요가 없다.
- 문제는 노트의 설명과 현재 코드에 근거한다. 노트의 이유가 `기록 없음`이면 `설계 이유` 문제는 내지 않는다.

**review의 문제 채우기 순서**
1. 미룬 퀴즈
2. 기록만 된 기능(`noted`): 기능마다 1문제 이상. 노트에 쓴다.
3. 틀렸던 개념
4. 전체 구조

- 3·4번만 `reviews/` 파일에 쓴다.
- 합계는 그대로 5~10문제다. 1번이 다 차지하면 2번 이하는 다음 review로 넘긴다.
- `noted` 기능이 많아 다 담을 수 없으면 오래된 것부터 담고, 남은 기능 수를 알린다.

**인자 없이 `/classmate`를 부를 때** (`explain-and-quiz.md`의 "직접 불렀을 때")
- 미룬 퀴즈와 함께 `noted` 기능도 알려주고 지금 풀지 묻는다.
- `noted` 기능은 기능마다 3문제(객관식 2 + 서술형 1)를 만들어 노트에 쓴 뒤 묻는다.
- 한 번에 최대 10문제. 넘치면 오래된 것부터 하고 남은 수를 알린다.

### 5.6 리포트

- 타임라인에서 `noted` 기능은 `기록만` 배지로 보인다. 퀴즈를 내면 상태가 바뀌어 배지도 바뀐다.
- `report-data.js`의 `features[].status` 값에 `noted`를 더하고, 그 기능의 `questions`는 빈 배열이다.

## 6. 처음 배우기 (`/classmate learn`)

### 6.1 명령

- `/classmate learn`: 처음이면 시작(6.2), 진행 중이면 다음 `대기` 장부터 이어서 한다. 모든 장이 `완료`면 `review`를 제안하고, 다른 영역을 더 볼지 묻는다. 더 보면 그 영역의 장을 같은 장 목록 끝에 이어 붙이고(장 번호는 이어서), 지도에 `- 추가 영역: …` 줄을 더한다. 기존 장과 상태는 지우지 않는다. *(제안)*
- `/classmate learn <장 번호>`: 그 장으로 간다.
- Codex는 `$classmate learn …`.

### 6.2 시작

1. `.classmate/config.json`이 없으면 난이도를 묻고 `{"enabled": false, "level": "<난이도>", "mode": "가볍게"}`로 만든다. `.gitignore`(`*`)도 만든다.
   - 전역 지침 파일은 건드리지 않는다.
   - `enabled: false`라서 기능 완성 자동 실행은 켜지지 않는다. 나중에 이 프로젝트에서 직접 개발하려면 `on`을 하면 된다.
2. 직접 만든 프로젝트인지 묻는다(`본인` / `다른 사람`).
3. **프로젝트 지도 만들기.** 아래만 읽는다.
   - README류 파일
   - 최상위 2단계까지의 폴더 구조. `node_modules`, `.git`, `dist`, `build`, `vendor`, `.venv` 같은 생성물과 의존성 폴더는 뺀다.
   - 패키지·설정 파일(`package.json`, `pyproject.toml`, `requirements.txt`, `go.mod`, `Cargo.toml` 등)
   - 진입점으로 보이는 파일의 앞부분
4. 지도를 보여준다.
   - 무엇을 하는 프로젝트인지
   - 어떻게 실행하는지(근거가 없으면 `알 수 없음`)
   - 큰 구조
   - 장 목록 3~8개. 장마다 제목, 다룰 파일·폴더, 한 줄 요약.
5. 프로젝트가 크면(최상위 폴더가 많거나 모노레포) 먼저 어느 부분을 공부할지 묻고, 장 목록은 그 범위로 만든다.
6. 지도와 장 목록을 `.classmate/learn.md`에 쓰고, 어느 장부터 볼지 묻는다.

### 6.3 `learn.md` 형식

```markdown
---
type: learn
owner: 다른 사람
started: 2026-11-26
---
# 프로젝트 지도
- 무엇: 할 일을 추가·완료·삭제하는 웹 앱
- 실행: index.html을 브라우저로 열기
- 구조: index.html(화면) · app.js(동작) · style.css(모양)

## 장 목록
| 장 | 제목 | 범위 | 상태 |
|---|---|---|---|
| 1 | 화면 뼈대와 시작 | index.html | 완료 |
| 2 | 할 일 추가 흐름 | app.js | 대기 |
```

- `owner`: `본인` | `다른 사람`
- 장 `상태`: `대기` | `완료`. 퀴즈를 미뤘어도 설명을 마친 장은 `완료`다. 미룬 퀴즈는 노트에 남는다.

### 6.4 장 하나 진행

1. 그 장의 `범위`에 있는 파일만 읽는다. 파일이 길면(대략 300줄 이상) 장 주제와 관련된 부분만 읽는다.
2. **쉬운 설명**(난이도를 따름, 10~15줄): 이 부분이 하는 일, 데이터 흐름 화살표 한 줄, 알아야 할 개념, 다른 장과의 연결.
3. **설계 이유**
   - `owner: 본인`: "그때 왜 이렇게 하셨는지 기억나세요?"라고 한 번 묻는다. 답하면 `이유: (본인 기억) …`, 모른다고 하면 `기록 없음`.
   - `owner: 다른 사람`: README, 관련 파일의 커밋 메시지(`git log`가 가능하면), 주석에서 찾는다. 찾으면 `이유: (추정, 출처: 커밋 abc123) …`처럼 출처를 붙이고, 없으면 `기록 없음`. 근거 없는 이유는 쓰지 않는다.
4. **노트**: 기존 학습 노트 형식으로 `features/`에 쓴다.
   - `feature: 2장 · 할 일 추가 흐름`
   - frontmatter에 `kind: learn`, `chapter: 2`를 더한다.
   - 흐름은 꼼꼼하게 모드와 같다: 노트를 미룸으로 먼저 저장 → 지금/나중에 → 퀴즈 3문제 → 채점·해설 → 노트 갱신.
   - 막혔던 것 줄은 `해당 없음`으로 쓴다.
5. `learn.md`의 그 장을 `완료`로 바꾸고, 다음 장을 제안한다.
6. 모든 장이 `완료`가 되면 `/classmate review`를 제안한다.

모드 설정은 learn에 적용되지 않는다. 사용자가 직접 부른 것이므로 항상 퀴즈를 묻는다.

### 6.5 review와 리포트

- review는 learn 노트를 다른 노트와 똑같이 다룬다.
- 전체 구조 설명에는 `learn.md`의 지도를 재사용해 코드를 다시 많이 읽지 않는다.
- 리포트 타임라인에는 장 노트가 `2장 · 할 일 추가 흐름`처럼 보인다.

## 8. 검증 (구현자가 세부를 정함)

시나리오 점검을 더한다.
- 가볍게: 기능 완성 → `noted` 노트, 한 줄 알림, 퀴즈 없음
- 가볍게: 5번째 노트에서만 중간 점검 제안
- 직접만: 아무 일도 없음
- `mode` 명령
- learn(다른 사람): 지도와 `learn.md`, 범위 밖 파일을 읽지 않음, 추정 표시
- learn(본인): 기억을 묻는 질문
- learn 이어서: `learn.md`의 다음 `대기` 장
- review: `noted` 기능을 다루는 문제
- 리포트: `기록만` 배지

- 직접 부르기: `noted` 기능 퀴즈가 노트에 써지고 상태가 바뀜

기존 S1~S14는 바뀐 지시문에 해당하는 것만 다시 돌린다. 기존 시나리오가 꼼꼼하게 모드를 전제하므로, 준비 단계에서 config에 `"mode": "꼼꼼하게"`를 넣는다.

## 9. 결정 기록

**사용자가 정한 것**
- 토큰 부담을 줄이는 빈도 모드를 둔다. 설계자 제안(가볍게 기본, 꼼꼼하게, 직접만)을 수락했다.
- 완성된 프로젝트용 기능을 만든다. 내 프로젝트와 남의 프로젝트 모두 대상이다.
- learn을 장 단위로 진행하는 설계자 제안을 수락했다.

**설계자가 정한 것** (본문에 *(제안)* 표시 포함)
- 명령 이름 `mode`, `learn`
- `mode`가 없으면 가볍게로 본다
- 중간 점검 제안은 noted 노트 수가 5의 배수일 때
- noted 기능에 퀴즈를 내면 문제를 그 노트에 쓰고 상태를 바꾼다(review와 직접 부르기 공통). 직접 부를 때도 noted 기능을 퀴즈 대상으로 삼는다
- learn에서 모든 장을 끝낸 뒤 다른 영역은 같은 장 목록에 이어 붙인다
- learn은 `on` 없이 동작하고 `enabled: false`로 config를 만든다
- 장 노트는 `features/`에 `kind: learn`으로 저장한다
- 장 상태는 대기/완료, 장 수는 3~8개, 읽을 범위와 긴 파일 처리 기준
- 남의 프로젝트의 이유는 출처를 붙인 추정으로만 쓴다
- GitHub 주소로 받아오기, 프로젝트 실행은 하지 않는다
